# RHOSO 18 Deployment Scripts

## Overview
Deployment scripts for TrilioVault (T4O) on Red Hat OpenStack Services on OpenShift (RHOSO) 18.0.
RHOSO 18 runs OpenStack services as Kubernetes/OpenShift workloads — control plane services are deployed as a Kubernetes Operator, data plane services are deployed via Ansible.

Reference: https://docs.redhat.com/en/documentation/red_hat_openstack_services_on_openshift/18.0/html/deploying_red_hat_openstack_services_on_openshift/index

## Architecture

| Plane | Deployment Method | Components |
|-------|------------------|------------|
| Control plane | Kubernetes Operator (via Helm) | wlm-api, wlm-workloads, wlm-cron, wlm-scheduler, dmapi |
| Data plane | Ansible | datamover (one per nova-compute node) |

## Technology Stack
- **Operator SDK / Go**: The TVO operator manages the lifecycle of Helm-released control plane services
- **Helm**: Kubernetes resource templating embedded inside the operator
- **OpenShift / Kubernetes**: CRDs, RBAC, Routes (OpenShift-specific ingress), OLM bundle format
- **Galera**: MySQL high-availability clustering for WLM and DMAPI databases
- **RabbitMQ**: Message broker for T4O service communication
- **Ansible**: Deploys and configures datamover on compute nodes

## Key Conventions

### Helm Chart Templates
- Config templates: `conf/_<component>-<purpose>.tpl` (e.g., `_api-paste.ini.tpl`)
- Init scripts: `scripts/_triliovault-<component>-<action>.sh.tpl`
- Kubernetes resources organised by service under `templates/`

### Operator Build
- `make` in `operator/tvo-operator/` builds and packages the operator
- `build/build_operator_image.sh` builds the operator container image
- `build/publish_operator.sh` pushes to registry
- OLM bundle format used for OperatorHub distribution

### Deployment Flow
1. `create-image-pull-secret.sh` — registry credentials
2. `create_cert_secrets.sh` — TLS certificates
3. `install_operator.sh` — install TVO operator
4. `deploy_tvo_control_plane.sh` — deploy control plane via operator
5. `dataplane-scripts/` Ansible roles — install datamover on compute nodes

## RabbitMQ CRD split (RHOSO <=18.0.18 vs >=18.0.21/FR6) — TVAULT-7511
- **RHOSO switched RabbitMQ operators at FR6 (18.0.21)**: <=18.0.18 uses the upstream community RabbitMQ Cluster Operator (`rabbitmq.com/v1beta1`, kind `RabbitmqCluster`); >=18.0.21 uses RHOSO's own native operator (`rabbitmq.openstack.org/v1beta1`, kind `RabbitMq`) and no longer deploys the community operator at all. T4O's chart ships two template variants — `templates/rabbitmq-till-18.0.18/` and `templates/rabbitmq/` (native, >=FR6) — and the build scripts (`build_operator_image.sh` / `devops-build-publish.sh`, `--openstack-version` flag) delete the non-matching directory (renaming the survivor to `rabbitmq` for the old variant) so a given operator image only ever ships one CRD kind. Install-time config is split the same way: `tvo-operator-inputs-till-fr5.yaml` / `tvo-operator-inputs-fr6-onwards.yaml`, auto-selected by `set_operator_inputs.py` based on `oc get openstackversion`.
- **Standalone infra CRs get NO image injection — T4O must always set the image itself**: RHOSO's own `rabbitmq`/`rabbitmq-cell1`/`openstack-galera` CRs carry a digest-pinned `registry.redhat.io` image only because `openstack-operator` copies `OpenStackVersion.status.containerImages.<x>Image` into the CRs *it* owns. A CR T4O creates directly is never reconciled by `openstack-operator`, and the controllers that do own it ship no `RELATED_IMAGE_*` env to fall back on (verified: `infra-operator-controller-manager`, which reconciles `RabbitMq` from FR6 on — there is no separate rabbitmq-operator Deployment in FR6 — has none). So an unset image field silently resolves to the controller's compiled-in **upstream community** default, e.g. `quay.io/podified-antelope-centos9/openstack-rabbitmq:current-podified` — unsupported by Red Hat and version-skewed from the platform broker. This is exactly how the FR6 `RabbitMq` CR shipped without an image (the native CRD's field is `spec.containerImage`, not `spec.image`, so it was wrongly assumed absent when the FR5 fields were pruned). **Rule: every infra CR the chart creates must set its image from `.Values.images.*`** — `containerImage` on `Galera` and native `RabbitMq`, `image` on the community `RabbitmqCluster`. Corollary: never add an `images.*` key to `FIELDS_TO_REMOVE` in `update_tvo_operator_inputs_to_latest.py` — stripping it from a customer's inputs file reintroduces the upstream default on their next upgrade.
- **Switching an existing FR6 broker off the upstream image rolls the StatefulSet, and that is safe on the existing PVCs**: because the `RabbitMq` CR is a plain manifest resource (TVAULT-7556), a `helm upgrade` patches `containerImage` in place, so infra-operator does a rolling restart onto the new image while `persistence-trilio-rabbitmq-cluster-server-0/1/2` keep the old broker's Mnesia database — no auto-generated credential is reminted, so this is *not* the PVC-reuse trap below. Direction matters though, and it was verified on a live FR6 setup: `quay.io/podified-antelope-centos9/openstack-rabbitmq:current-podified` is RabbitMQ **4.2.6** and `registry.redhat.io/rhoso/openstack-rabbitmq-rhel9:18.0` is **4.2.7**, both on Erlang OTP 26 — a forward patch-level upgrade, so the schema and feature flags open cleanly and no CR/PVC deletion is required. Check both versions with `rabbitmqctl version` before any future change of this image; a *backward* jump (older binary against a schema with newer feature flags already enabled) would CrashLoopBackOff all three brokers and take dmapi/wlm AMQP down, and would need the CR+PVC delete.
- **Never pin an infra image to a floating `:18.0` tag — use the version-specific tag (`:18.0.21`)**: pods are created with the default `imagePullPolicy: IfNotPresent`, so a node that pulled `registry.redhat.io/rhoso/openstack-rabbitmq-rhel9:18.0` months ago keeps serving its cached copy forever and never sees the current content. Reproduced on the FR6 QA cluster: the registry served `sha256:7531e00b` (RabbitMQ **4.2.7**) for both `:18.0` and `:18.0.21`, but the broker pods resolved `:18.0` from node cache to `sha256:ff08c305`, a **3.x** build. Because infra-operator generates a 4.x `rabbitmq.conf` for `queueType: Quorum`, the old broker refused to boot: `Conf file attempted to set unknown variable: queue_leader_locator` / `quorum_queue.continuous_membership_reconciliation.*` → `BOOT FAILED ... {error,failed_to_prepare_configuration}`, all three pods CrashLoopBackOff. The tell-tale is the 3.x hint *"Did you mean queue_master_locator?"* — a 4.x broker would accept the key. Diagnose with `oc get pod ... -o jsonpath={.status.containerStatuses[0].imageID}` (the **resolved digest**, not `.spec.containers[].image`) and compare against `oc image info <ref> --registry-config=<pull-secret>`; extract the secret via `oc get secret -n openshift-config pull-secret -o jsonpath='{.data.\.dockerconfigjson}' | base64 -d`. FR6 inputs therefore use `:18.0.21`; till-FR5 stays on `:18.0` (community operator, config suits the older broker). Note `values.yaml`'s `images.rabbitmq` chart default is still `:18.0` — it is only a fallback for an inputs file missing the key, but it carries the same staleness risk.
- **A `pending-install` helm release cannot be upgraded — the only way out is uninstall + reinstall**: if any post-install hook Job never succeeds, the release is stuck at `status=pending-install` (check `oc get secret sh.helm.release.v1.<name>.v1 -o jsonpath={.metadata.labels.status}`). While stuck, editing `tvo-operator-inputs.yaml` and re-applying is silently useless: the TVOControlPlane's `spec` updates but the operator can never run the upgrade, so the rendered child resources keep the old values — you see the CR say one thing and the `RabbitMq`/`Galera` CR say another. This is self-inflicting with a broken broker image: `job-triliovault-datamover-api-rabbitmq-init` retries `RabbitMQ API not reachable` forever, pinning the release. Patching the child CR out-of-band unblocks the boot but does not fix the release; run `uninstall_tvo_control_plane.sh`, delete `persistence-trilio-rabbitmq-cluster-server-{0,1,2}` (see the PVC-reuse rule below), then `deploy_tvo_control_plane.sh` with corrected inputs.
- **`registry.redhat.io/rhoso/*` images pull from `trilio-openstack` with no namespace pull secret**: the namespace has no `kubernetes.io/dockerconfigjson` secret of its own, yet `trilio-galera-cluster` runs `registry.redhat.io/rhoso/openstack-mariadb-rhel9:18.0` — the cluster-wide pull secret covers it. So pinning a `registry.redhat.io/rhoso/…:18.0` image in the inputs file needs no extra credential work.
- **Never reuse RabbitMQ PVCs across a CRD-kind change**: each RabbitMQ CR (either kind) generates a fresh, randomly-generated `<name>-default-user` secret on creation, but a reused PVC still has the *old* broker's persisted Mnesia database with the *old* credentials baked in. The mismatch surfaces as `job-triliovault-datamover-api-rabbitmq-init` stuck retrying "RabbitMQ API not reachable" (traces to `401 Unauthorized` on the management API) — confirmed by direct reproduction during 6.1 testing. Any migration between CRD kinds (or even a delete+recreate of the same kind) must also delete `persistence-trilio-rabbitmq-cluster-server-0/1/2` (same PVC naming on both variants), not just the CR.
- **Never make a stateful/identity-bearing CR a Helm hook without a delete-policy (TVAULT-7517)**: `rabbitmq-cluster.yaml` (both chart variants) used to be tagged `helm.sh/hook: post-install,post-upgrade` with no `hook-delete-policy`. Helm's *documented default* for an unset `hook-delete-policy` is `before-hook-creation` - it deletes the existing hook resource and recreates it fresh on **every** hook firing, i.e. on every single `helm upgrade`, not just the first install. Since the RabbitMQ operator (community `RabbitmqCluster` or native `RabbitMq`, either one) auto-generates a random `default-user` secret whenever the CR object is created, this meant **any** subsequent `oc apply` of `tvo-operator-inputs.yaml` - even one that never touched a rabbitmq field - deleted and recreated the RabbitMQ CR, minting a fresh secret while the StatefulSet's PVCs kept the old Mnesia data/credentials, breaking datamover-api/wlm auth. Confirmed via CR/secret UID and creationTimestamp changing across an unrelated second apply. Occasionally this also raced with the object's own finalizer-driven deletion and failed the hook outright (`object is being deleted: rabbitmqs.rabbitmq.openstack.org "trilio-rabbitmq-cluster" already exists`), rolling back the whole release - same root cause, just the failure-mode half of it. Originally fixed by removing the hook annotations entirely so the CR became a normal templated resource - see PRs #1543 (maint/6.1) / #1544 (maint/6.2). **That fix was superseded by TVAULT-7556 (see next bullet): de-hooking the CR broke every upgrade from a release where it had been a hook.** General lesson: don't tag a CR as a Helm hook if its controller mints persistent, randomly-generated state (secrets, tokens) on creation *and* the hook fires on upgrade - the safe combination is an install-only hook.
- **Never flip a resource between hook and non-hook across releases (TVAULT-7556)**: Helm hook resources are excluded from the release manifest and are never stamped with Helm ownership metadata (`app.kubernetes.io/managed-by: Helm`, `meta.helm.sh/release-name`, `meta.helm.sh/release-namespace`). So when TVAULT-7517 de-hooked `rabbitmq-cluster.yaml`, the next upgrade tried to adopt the already-existing CR as a regular manifest resource and Helm refused: `failed to get candidate release: ... invalid ownership metadata; label validation error: missing key "app.kubernetes.io/managed-by"`. This aborts **before a candidate release is even built**, so no hooks run and no Deployments are updated - the visible symptom is "control plane configured but pods still on the old image", with the release stuck at its previous revision. Reproduced end-to-end on the FR5 setup upgrading 6.2.0 -> 6.2.1-maint-7.2 (release stayed at revision 1, all pods on 6.2.0). **Fixed by keeping both cluster CRs as plain templated (non-hook) resources and stamping the missing ownership metadata once, via `patch_helm_ownership_metadata.sh`.** An install-only hook (`helm.sh/hook: post-install`) was tried first and does dodge the ownership check, but it freezes the CR spec after install and is not self-healing, so it was rejected in favour of the adoption patch. The patch is idempotent (objects already carrying correct metadata are skipped), derives the release name from the TVOControlPlane CR rather than hardcoding it, and must run for **any** upgrade originating from 6.1.x or 6.2.0 regardless of the 6.2.x target.
- **`patch_helm_ownership_metadata.sh` is an upgrade-only step and is deliberately NOT called from `deploy_tvo_control_plane.sh`**: it was originally wired into that script, but the deploy script is also the fresh-install entry point and a fresh install never needs the patch (there is no pre-existing CR to adopt), so the call was removed to keep the install path free of upgrade-only steps. It is now run manually, immediately *before* `deploy_tvo_control_plane.sh`, and the ordering is load-bearing — the metadata must be stamped before `tvo-operator-inputs.yaml` is applied, because applying the CR is what triggers the helm-operator's upgrade. Run it after the exec bit is set (`chmod +x`); it ships from git as mode `100755`, but a tarball/zip transfer or a `scp` onto the bastion can drop the bit. The upgrade procedure carries both steps — see the Confluence page "T4O 6.2 Install and Upgrade Step Changes For RHOSO18" (page 4973297665). If this step is skipped the upgrade fails silently: Helm aborts before building a candidate release, so the control plane reports as configured while every pod stays on the old image.
- **The Galera CR had the identical delete+recreate bug, unfixed until TVAULT-7556**: `galera-cluster.yaml` was `helm.sh/hook: post-install,post-upgrade` with no delete policy, so Helm's default `before-hook-creation` deleted and recreated it on **every** `helm upgrade` - confirmed by the CR uid/creationTimestamp changing on each upgrade. This tore the MariaDB StatefulSet down mid-upgrade, and the *previous* revision's wlm/dmapi pods - still running, because Helm had not yet reached the Deployment hooks at weight 100-104 - lost their database and crash-looped (`set -e` start scripts, and **no liveness/readiness probes** on the wlm containers, so a failed start just exits). This is the real cause of the "control plane pod crashed 5-9 times before running" reports (TVAULT-7519), *not* the `job-triliovault-wlm-cloud-trust` hook weight of 150: the trust already exists on an upgrade. Newly-created pods never crash because hook ordering guarantees the DB is back before they start, which is why the restart count appears to reset. Data was never lost - PVCs come from the StatefulSet's `volumeClaimTemplates` and are not garbage-collected with it, so the rebuilt cluster re-binds the same PVs (verified: `workloadmgr` and `dmapi` databases intact across two recreates).
- **Galera is safe to delete+recreate on the same PVs; RabbitMQ is not**: Galera's credentials come from a fixed pre-existing secret (`spec.secret: trilio-openstack-secret`), so a recreate re-binds the existing PVCs and the data still opens. RabbitMQ's `<name>-default-user` secret is *auto-generated* on CR creation, so a recreate mints credentials that no longer match the Mnesia database on the reused PVC. Use this distinction when deciding whether a given CR can be recreated as a recovery step.
- **Manifest resources are applied before post-install/post-upgrade hooks**, so de-hooking the cluster CRs did not need replacement hook weights: the CRs still exist before `galera-cluster-wait-job` (`-13`) and the rabbitmq wait-job (`-17`) run. Being in the manifest also makes them self-healing - deleting either CR out-of-band is repaired by the next upgrade, whereas a hook resource would not be recreated.
- **Release image tags**: `https://docs.trilio.io/openstack/about-trilio-for-openstack/artifacts/<version>` (e.g. `.../6.1.9`) lists the exact published image URLs/tags for that T4O release — check here rather than guessing tag strings when testing/upgrading against a real release.
- **`dmapi`/`workloadmgr` RabbitMQ credentials are independent of the RabbitMQ CR's lifecycle**: the `dmapi` user's password is a fixed value in `trilio-openstack-secret` (`DmapiRabbitPassword`), not derived from the cluster's own auto-generated `<name>-default-user` secret. This means datamover's connection config never needs to change across a RabbitMQ CR recreate — the rabbitmq-init hook Jobs re-declare the same fixed-password users against the new broker, and datamover's own AMQP client auto-reconnects and redeclares its queues/exchanges without needing a restart or redeploy. Confirmed via a genuine operator-image upgrade test (real 6.1.9 GA operator → fix operator, RabbitMQ CR+PVCs deleted/recreated by the upgrade) with datamover left running untouched the entire time — a real backup completed successfully afterward.
- **Always validate hook/upgrade behavior with a genuine operator image swap, not a CR-spec toggle.** Confirmed via a full real-upgrade test (uninstall everything → install the actual unmodified 6.1.9 GA operator → in-place image swap to the fix build, no CR/spec changes) that a real operator upgrade correctly and automatically re-runs every Helm hook Job on its own, including both rabbitmq-init Jobs — no manual Job deletion or `hook-delete-policy` change needed anywhere in the chart. Forcing a Helm reconcile by patching an unrelated CR spec field instead of swapping the operator image does not reliably exercise the same hook re-execution path, so it's not a valid way to test upgrade/hook behavior.

## Known Constraints
- **`workloadmgr backup-target-list --format json` mixes target types**: the output includes a `Type` field (`"s3"` / `"nfs"`, compare case-insensitively) alongside `Backend Endpoint` and `ID`. For S3, `Backend Endpoint` is a plain bucket name or `host:port/bucket` (take the last `/`-separated component). For NFS, `Backend Endpoint` is the share path itself (e.g. `host:/export`) — do **not** split on `/`, that truncates the path into a false identifier (this caused TVAULT-7419's phantom bucket-name mismatch). Confirmed against the same CLI schema in `juju-charms/upgrade_backup_targets_62.sh`.
- **T4O 6.0/6.1 NFS backup target field names** (`tvo-operator-inputs.yaml` `spec.triliovault_backup_targets[]` and `TVOBackupTarget` CR `spec.triliovault_backup_target`): `backup_target_type: 'nfs'`, `nfs_shares` (export path, e.g. `'192.168.2.3:/nfs/share'`), `nfs_options` (mount options string). Parallel to the `s3_*` fields already used for S3 targets. These aren't documented anywhere in the `maint/6.2` tree — the CRD (`tvo.trilio.io_tvobackuptargets.yaml`) and sample CR templates (`tvo-backup-target-cr-nfs.yaml`, `tvo-backup-target-cr-*-s3.yaml`) only exist on `maint/6.1`; they were dropped before `maint/6.2` since 6.2 stopped managing backup targets via devops scripts. Check `git show maint/6.1:redhat-director-scripts/rhosp18/ctlplane-scripts/<file>` when you need the real schema.
- **NFS backup targets need no Barbican secret in the 6.1→6.2 migration**: `update_backup_targets_62.sh` intentionally skips NFS entries — only S3 credential storage moves from k8s Secrets to Barbican in 6.2; NFS backup target records are unchanged. This is documented behavior (see the Confluence page "T4O 6.2 Install and Upgrade Step Changes For RHOSO18"), not a bug — don't try to add Barbican secret creation for NFS there.
